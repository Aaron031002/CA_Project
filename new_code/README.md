# New CBI architecture simulator

This is the simulator for the new CBI project (inherited from the previous
project's code, since rewritten). It is a cycle-level, SystemC-based model of
a many-core accelerator: a 2-D mesh of `Core`s (each with an Array unit,
Vector unit, TMU, DMA, local DRAM/cache) connected by a NoC, plus a
`GlobalSyncManager` for barrier synchronization and a `DRAMRouter` for
cross-core DRAM access. This file explains how the simulator is configured,
how it consumes input tensors/instructions, how it produces output, and how
to build and run it.

**This handout is a dense-MLP workload** — one MNIST-classifier MLP
(`small_mlp`, 784 → 128 → 64 → 32 → 16 → 10) at batch size 1, on a **fixed
2×2 mesh** (4 cores, XY routing) — not the transformer/MoE/RPC workload an
earlier version of this codebase ran. §3-§6 below describe that MLP
pipeline's actual input/output data layout and how to run it.

**Where the specs live**: the SystemC module hierarchy / per-`Core` wiring /
`MainCtrl` control flow is [curr_arch.md](curr_arch.md); the full
instruction text grammar (every opcode's fields) is
[inst_spec.md](inst_spec.md). This file only covers configure/build/run and
the data layout — not what each instruction does internally.

## 1. Configure

Hardware/model/workload parameters are defined once in YAML and turned into
C++ headers at CMake configure time — there is nothing to hand-edit in the
generated headers.

- `config/hardware.yaml` — NoC (mesh size, lanes, buffer depth, router/link
  delay...), DRAM (bus width/bandwidth, cross-core "rail" overhead, off-chip
  overhead...), Cache (`dual_port`, `max_capacity_bytes`, `bus_width_bits`,
  `arbiter_mode`: `default` fixed-priority scan vs `parallel` per-port).
- `config/model.yaml` — model shape (`d_model`, `n_heads_q`, `n_heads_kv`,
  `head_dim`, `n_experts`, `top_k`, `ffn_dim`, `sliding_win`), sized for a
  gpt-oss-20b-like architecture.
- `config/workload.yaml` — per-run sizing: `kv_cache_batch_capacity`,
  `max_seq_len`, `num_layers`.

`tools/gen_config_headers.py` reads these three files and regenerates four
headers (its `TARGETS` dict):
- `NoC_sim/noc_param.h` ← `hardware.yaml`'s `noc:` block
- `DRAM_sim/dram_params.h` ← `hardware.yaml`'s `dram:` block + `model.yaml`'s
  `head_dim`/`n_heads_kv` + `workload.yaml`'s `kv_cache_batch_capacity`/
  `max_seq_len`/`num_layers`
- `Core/MainCtrl/main_ctrl_params.h` ← `model.yaml`'s `d_model` only (the
  rest of that header, e.g. `DYNAMIC_PKT_BASE`, is still hand-maintained)
- `Core/Cache/cache_params.h` ← `hardware.yaml`'s `cache:` block

This script is invoked automatically by `CMakeLists.txt` via
`execute_process(...)` during `cmake ..` — every configure re-syncs the
generated headers with the YAML, so editing a `.yaml` file and re-running
`cmake ..` is enough to change these parameters simulator-wide. Some
module-local constants (Array/Vector/DMA/TMU/MainCtrl/off-chip DRAM sizing)
are not yet migrated to YAML and are still hand-edited in each module's
`*_params.h` (see comments in `config/hardware.yaml` for current migration
status).

## 2. Build

**Environment**: the supported environment is the Docker image
built from the repository root's [`Dockerfile`](../Dockerfile); see
[USER_GUIDE.md](../USER_GUIDE.md) Part 1. For a native build, set
`SYSTEMC_HOME` to your SystemC install directory (containing
`include/systemc.h` and `lib/libsystemc.*` or `lib-linux64/libsystemc.*`)
and activate the `ca_fp_2026` conda env before running `cmake`. `cmake` also
falls back to `/usr/local` and `/usr` if `SYSTEMC_HOME` is unset; if none
resolve, configure fails with an error naming this requirement.

Always build out-of-source under `new_code/build/`, never `cmake .` inside
`new_code/`.

### The MLP testbench: auto-discovered `*_Acc.cpp`

Every source file under `new_code/test/` matching `*_Acc.cpp` becomes its own
build target (`file(GLOB "*_Acc.cpp")` in `test/CMakeLists.txt`, re-scanned
on every `cmake ..`). The `small_mlp` testbench is generated by
[`run_scripts/gen_acc_from_case.sh`](../run_scripts/gen_acc_from_case.sh):

```bash
# from the repo root
bash run_scripts/gen_acc_from_case.sh   # -> new_code/test/small_mlp_Acc.cpp

cd new_code/build                    # mkdir -p it the first time
cmake ..                             # re-scan for new *_Acc.cpp files
cmake --build . --target small_mlp_Acc
```

or, equivalently, [`new_code/build.sh`](build.sh), which re-runs `cmake ..`
and builds `small_mlp_Acc`:

```bash
bash new_code/build.sh                  # small_mlp_Acc
bash new_code/build.sh -j8              # parallel build
```

The binary lands in `new_code/build/bin/small_mlp_Acc`. The generated `.cpp`
drives the shared `Acc8x8<T>` mesh (`Acc/acc_8x8.h`/`.cpp`, compiled once
into `acc_lib`) with a **fixed 2×2 mesh and XY routing**, built into the
testbench (the mesh size in `hardware.yaml` is not used for it, and any
`acc_config.yaml` in the case folder is ignored).

### CMake options (all `OFF` by default)

| Option | What it enables |
|---|---|
| `ENABLE_DEV_TESTS` | Every hand-written target in `test/CMakeLists.txt` (unit tests such as `test_noc`/`test_dram`/`test_cache`, and system tests). Their sources under `test/` are not shipped with this handout, so turn it on only in a tree that has them |
| `ENABLE_TRANSFORMER_TESTS` | The inherited transformer/attention/MoE test targets (inside the `ENABLE_DEV_TESTS` block, so they need it too). Several of their sources no longer exist on this branch |
| `ENABLE_DYNAMIC_DISPATCH` | The DRAM group/off-chip/fallback/residency mechanisms the MLP workload doesn't use |

With the defaults, `cmake --build .` builds only the generated `*_Acc`
testbenches (plus the simulator libraries they link).

## 3. Input: instructions — this is what YOU write

Each `Core` in the mesh runs its own independent instruction stream, read as
a plain-text file:

```
<inst_dir>/core_<i>_insts.txt      // one file per core, i = 0 .. 3
```

`<inst_dir>` is the case directory `inst_gen/MLP_small_mlp/B1/`. **Producing
this directory's contents — the `core_<i>_insts.txt` files and
`dram_map.yaml` — is your job, not something this repo generates for you.** Full field-by-field opcode grammar:
[inst_spec.md](inst_spec.md); what `MainCtrl` does with each opcode:
[curr_arch.md](curr_arch.md). The grammar covers far more than a dense MLP
forward pass needs (attention ops, RPC, etc. are inherited engine
capability from an earlier transformer/MoE workload this branch doesn't
use) — the opcodes actually relevant here are `DMA DRAM read/write`,
`DMA NoC send/recv`, `Array NORMAL`, `Vector BIAS_ADD`/`RELU`/`SOFTMAX`,
`TMU concat`, and `TCore LOCAL_SYNC`/`GLOBAL_SYNC`.

`#` starts a comment (at the start of a line or after whitespace), and blank
lines are ignored. Every other line must match the grammar exactly: an
unknown opcode or mode, a missing or non-numeric field, or a leftover token
stops the simulation before it starts with
`Fatal: MainCtrl/DECODE: core <i>, <file>:<line>: <reason>`.

Alongside `core_<i>_insts.txt`, each case directory also needs its own
`dram_map.yaml` (DRAM ownership map — §4) — also something you produce,
not something generated for you. Its schema (`AddressMapper::load()`,
`new_code/DRAM_sim/AddressMapper.cpp`):

```yaml
version: 1
num_cores: 4             # must be 4 (the fixed 2x2 mesh)
entries:
  - path: "<repo-root-relative path, e.g. new_code/DRAM_sim/DRAM_data/in_tensor/mlp/in_B1.bin>"
    owner: 0              # single owning core, OR:
  - path: "<...>"
    owners: [0, 1, 2, 3]  # replicated across multiple cores
```

Every file a `DMA DRAM read/write` instruction touches needs an `entries`
row here naming which core(s)' local DRAM physically hold it — this is
pure ownership/routing metadata (which core's local DRAM to resolve a read
against), never tensor data itself, and is loaded once, synchronously,
before the simulation starts (`DataManager`'s constructor). This pipeline
never needs `dram_group.bin`/`offchip_map.yaml` (leave those constructor
arguments empty, as the generated `*_Acc.cpp` testbenches already do) —
every weight/input read targets the executing core's own local DRAM
directly, no cross-core group access required.

## 4. Input: tensors / weights — this is provided to you

Instructions address tensor bytes by file path (`DMA DRAM read/write
<file_name> index <row_s> <row_e> <col_s> <col_e> ...` — flat `float32`, no
header). Everything lives under `new_code/DRAM_sim/DRAM_data/` (gitignored/
unversioned — this is where the files handed out alongside this repo go;
unlike §3's instructions/`dram_map.yaml`, you do not generate these
yourself). Two kinds of file:

- **Model weights** — `model_weight/mlp_bin/small_mlp/layer<N>_{weight,bias}.bin`
  (N = 0..4), one pair per linear layer, plus that directory's
  `manifest.json`. Provided pre-converted from the trained checkpoint (also
  provided, `model_weight/5mlp_weight/small_mlp/small_mlp_mlp_model.pth` +
  `config.json` — used by `run_scripts/compare_output_mlp.py`'s reference
  forward pass, §6, not read by the simulator itself).
- **Input activations** — `in_tensor/mlp/in_B1.bin` (1 row × 784 cols, one
  flattened MNIST image) + `labels_B1.bin` (int32 ground-truth label, for
  the offline accuracy check only — the simulator itself never reads
  labels).

Your own instruction stream (§3) is what actually ties `in_B1.bin` and the
`layer<N>_*.bin` files together — via each file's `DMA DRAM read` calls and
its `entries` row in your own `dram_map.yaml`.

## 5. Execution

(Module wiring / control-flow internals: [curr_arch.md](curr_arch.md) §1-§2
— this section is only the run recipe.)

Once your own `core_<i>_insts.txt`/`dram_map.yaml` (§3) sit under
`inst_gen/MLP_small_mlp/B1/`, build the testbench binary (§2 has the full
explanation — short version):

```bash
bash run_scripts/gen_acc_from_case.sh
cmake -S new_code -B new_code/build          # creates new_code/build/ if needed
cmake --build new_code/build --target small_mlp_Acc
```

Then run the case directly, **from the repository root** (file paths in the
instructions and `dram_map.yaml` are relative to it; anywhere else the
testbench stops with `[ERROR] Run this from the repository root ...`):

```bash
new_code/build/bin/small_mlp_Acc <inst_dir> [<output_file> <batch> <num_classes>]

# e.g.:
new_code/build/bin/small_mlp_Acc \
  inst_gen/MLP_small_mlp/B1 \
  new_code/DRAM_sim/DRAM_data/out_tensor/mlp/small_mlp_out_B1.bin \
  1 10
```

The last three arguments are optional — omitting them still runs the full
simulation, just skips the testbench's own output-file sanity check (file
exists / right size / all values finite).

Or use the quick runner, which fills the output file with NaN first (so a
value the run doesn't write can't pass as a stale result from an earlier
run) and saves the logs. It is for debugging;
[`run_scripts/score_mlp.py`](../run_scripts/score_mlp.py) is the full check
and the one to trust (see USER_GUIDE.md §15):

```bash
bash run_scripts/run_mlp_configs.sh
```

What either way produces:
- stdout/stderr — printed directly to your terminal for a direct binary
  invocation, or (quick runner) redirected to
  `sim_logs/mlp_small_mlp_B1.{stdout,stderr}`. `[TB] ...` lines are
  simulation progress/watchdog output; `[ OK ]`/`[FAIL]` lines plus a final
  `N checks, M failures` line are the testbench's own sanity checks.
- The result tensor itself — see §6.

## 6. Output

- **Output tensor**: `new_code/DRAM_sim/DRAM_data/out_tensor/mlp/
  small_mlp_out_B1.bin` — flat `float32`, shape `[1, 10]`
  (post-softmax class probabilities). Where in your own instruction stream
  this gets written is up to you (§3) — the simulator itself has no notion
  of a "classifier stage," it just executes whatever `DMA DRAM write`
  instructions you emit.
- **Accuracy / numerical verification** (a self-check step — not run
  automatically by either the binary or the sweep script):
  ```bash
  python3 run_scripts/compare_output_mlp.py
  ```
  Recomputes the same forward pass in PyTorch straight from the provided
  `.pth` checkpoint + `in_B1.bin`, diffs it against the `.bin` above
  (max abs diff + softmax-argmax match), and also reports classification
  accuracy against the ground-truth label. Prints `PASS`/`FAIL` and exits nonzero on failure.
  Use this to check your own instruction stream's output before assuming a
  discrepancy is a simulator bug.
- **Full check**: `python3 run_scripts/score_mlp.py` checks the case files
  (allowed DRAM reads/writes, 4 core files, `num_cores`), runs the case,
  checks that this run wrote the output and that it passes
  `compare_output_mlp.py`, and prints PASS with the latency in cycles. See
  USER_GUIDE.md §15.
- **Logs**: per §5 above — all simulator/runner logs land under
  `sim_logs/` at the repo root, never `/tmp`.
